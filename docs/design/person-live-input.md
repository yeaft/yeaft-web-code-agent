# Person：执行中连续收信与按消息回应

## 交互语义

数字人的输入不再与执行器绑定为“一问一答锁”。同一用户可以在数字人请求模型、执行工具、等待后台结果或暂停时继续发送文本和附件。

- 每条发送都是独立、可持久核对的用户消息，保留 `clientMessageId` 和消息 ID。
- 忙碌时的消息进入当前 episode 的收件箱，不另外启动一个共享 workspace 的写入 loop。
- 相关补充、限制和纠正进入当前执行；不相关的问题可以在同一执行中分别回答。
- 不以关键词或额外分类模型强行切分话题，也不要求用户发送前选择“排队／打断／新话题”。
- Send 可以继续使用；Think / Dream 仍然是空闲触发，避免叠加第二条认知执行。

**执行 episode、用户消息和回答不是一对一关系。** 一个 episode 可以消费多条用户消息，也可以发布多份独立回答。它们共享连续的实际执行与证据，而不是多个隐形 Session。

## 接收与执行边界

发送 ACK 只表示消息已持久接收，不表示模型已经读过，更不表示任务完成。用户消息展示区分：

- `queued`：已收到，尚未交给当前执行。
- `received`：已交给当前执行，不承诺语义上已经正确理解或完成。
- `stopped`：原执行已停止，未消费的消息仍保留，不自动重放。

运行中的请求或工具不因普通补充被强杀。当前操作结束后，在安全边界消费新增消息；较旧模型响应中尚未派发的工具不再按旧指令执行，而返回明确的未执行结果，让模型依据新消息重新选择。已完成操作、原始输出、费用和 trace 保留，不伪装回滚。

收件箱版本与原有 admission / lease / state fencing 分离。新消息不应使正在归档的真实操作结果变成过期写入；但下一次派发、终局输出和认知提交必须核对是否还有未纳入的新输入，防止在新限制已到达后按旧请求继续执行或提交。

暂停期间允许接收，不能绕过暂停去请求模型或派发工具。取消、失权、存储失败和进程中断仍优先，不能因为收件箱里有消息就复活旧任务。正在进行的不可撤回操作仍可能完成；普通发消息不是取消或回滚协议。

## 分别回答与可见归属

`Conversation.reply` 在连续工具 loop 内发布一份针对已消费消息的独立文本回答：

- 参数为准确的 `messageIds` 和 `text`。
- 只能引用本 episode 中真正交给执行的用户消息，不能引用其他用户、未消费消息或不存在的消息。
- 同一个调用身份重试不会重复发布。
- 回答带 `replyToMessageIds`，界面展示已加载用户消息的简短引用；目标不在窗口时明确保留引用身份，不猜测内容。
- 相邻助手记录只有回应目标相同时才合并，避免把不同问题的答案挤成同一个巨型 turn。

普通文本输出仍然有效；执行最终输出和最终认知回复保留所消费用户消息的关联。这种关联表示回答范围，不是自动证明每个问题都已解决。独立回答本身也不是修改代码或验收完成的执行证据。

新增消息不自动取消旧承诺。数字人应把相关修正纳入原目标，对其他问题分别答复，并持续处理未撤销工作。发生真实优先级冲突、授权不明或需要用户取舍时，才明确说明阻塞。

## 兼容与验证边界

数据字段为 additive，旧消息没有 delivery / reply 字段时沿用旧展示。Server 继续负责认证归属和中继，不负责主题判断，也不执行模型。未知发送结果仍使用原 `clientMessageId` 查询 receipt；不能用新 ID 盲目重发。

验证重点是消息不丢失、幂等与 owner 隔离、暂停取消、模型／工具批次／等待／最终提交的竞态，以及明暗主题和窄屏可用性。脚本化模型可以验证这些机制，不能证明真实模型总能正确识别关联性、优先级或完整回应所有事项。
